# Методология анализа

## Единица наблюдения

Исходная строка данных Expedia представляет собой агрегированную запись
журнала, а не обязательно одно физическое действие пользователя. Поле `cnt`
показывает, сколько одинаковых событий объединено в этой строке.

Поэтому в проекте используются два способа измерения объёма:

- `row_events = COUNT(*)` — количество строк;
- `weighted_events = SUM(cnt)` — количество событий с учётом их кратности.

Эти показатели нельзя смешивать в одной формуле. Для каждой конверсии должен
использоваться согласованный числитель и знаменатель.

## Расчёт основных конверсий

### Конверсия по строкам

```text
booking_row_rate = bookings / row_events
```

Показывает долю строк, в которых `is_booking = 1`.

### Конверсия с учётом `cnt`

```text
booking_weighted_event_rate =
    SUM(cnt для строк с is_booking = 1) / SUM(cnt для всех строк)
```

Показывает долю бронирований среди событий с учётом количества одинаковых
действий, объединённых в строке.

### Конверсия сессий

```text
session_booking_rate = booking_sessions / sessions
```

Показывает долю восстановленных сессий, в которых было хотя бы одно
бронирование.

## Слои данных

| Слой | Назначение |
|---|---|
| `RAW` | Неизменённое представление исходных файлов `Parquet` |
| `STAGING` | Приведение типов, разбор дат, разметка дубликатов и добавление признаков качества |
| `CORE` | Контролируемое удаление дубликатов, таблицы фактов, справочники и производные признаки |
| `MARTS` | Агрегированные витрины для продуктового анализа и отчётности |

Полная архитектура проекта: `RAW → STAGING → CORE → MARTS`.

Полные дубликаты удаляются контролируемо: из каждой группы одинаковых исходных
полей сохраняется первая строка по стабильному порядку `source_row_id`. При
сборке `CORE` удалено `969` повторяющихся строк.

## Даты

Допустимый диапазон дат проекта — с `2013-01-01` по `2016-12-31`
включительно. Он применяется к датам события, заезда и выезда.

Строки с некорректными датами сохраняются в `STAGING` и `CORE`, но не участвуют
в расчётах, для которых требуется корректная дата. Для дат за пределами
диапазона не назначается ключ из `core.dim_date`, а зависимые показатели
остаются `NULL`.

Большинство полей `year_month` в CSV хранится как дата первого дня месяца,
например `2014-07-01`. 

Поведенческие события относятся к 2013–2014 годам. Итоговый файл
`mart_travel_calendar_daily.csv` содержит непрерывную календарную ось с 15
февраля 2012 года по 13 января 2031 года, поскольку объединяет даты событий,
заездов и выездов. Для продуктового анализа необходимо ограничивать период
корректным диапазоном наблюдения.

## Восстановление сессий

В источнике нет готового идентификатора сессии. Сессии восстанавливаются по
правилу `gap_30m_v1`:

1. события каждого пользователя сортируются по `event_ts` и `event_id`;
2. новая сессия начинается, если между соседними событиями прошло строго более
   30 минут;
3. события с одинаковым временем остаются в одной сессии;
4. изменение направления, канала, устройства или параметров поиска само по
   себе не начинает новую сессию;
5. значение `cnt` не влияет на границы сессии.

В результате из `37 669 324` допустимых строк событий получено `12 242 331`
сессий. Это аналитическая реконструкция, а не исходная сущность Expedia.

Связь события с сессией хранится в `core.event_session_map`, а агрегированные
характеристики сессий — в `core.fct_session`.

## Бронирования

- `bookings` — количество строк с `is_booking = 1`;
- `bookers` — количество уникальных пользователей хотя бы с одним
  бронированием;
- `booking_sessions` — количество восстановленных сессий хотя бы с одним
  бронированием.

В данных фиксируется факт бронирования, но нет отдельной информации об оплате,
способе оплаты или фактическом проживании.

## Условная ценность бронирования

Поле `booking_value_proxy` используется как относительный показатель:

- `0` — событие без бронирования;
- `1` — бронирование только гостиницы;
- `2` — пакетное бронирование.

Этот показатель нельзя интерпретировать как цену, оборот, выручку, прибыль или
денежную сумму. Он позволяет только условно учитывать более высокую ценность
пакетного бронирования относительно бронирования одной гостиницы.

## Параметры поездки

Срок до поездки рассчитывается как разница между датой заезда и датой события:

```text
lead_days = checkin_date - event_date
```

Длительность проживания рассчитывается как разница между датой выезда и датой
заезда:

```text
stay_nights = checkout_date - checkin_date
```

`lead_days` заполняется только для записей с корректными датами события и
заезда. `stay_nights` заполняется только для записей с корректными датами
заезда и выезда. Проживание с заездом и выездом в один день исключается из
анализа длительности, поскольку его бизнес-смысл неоднозначен.

## Восстановление пропущенных расстояний

В поле `orig_destination_distance` отсутствует около 35,9% значений. Пропуски
заполняются медианой по географическим группам при наличии минимум пяти
известных расстояний.

Группы проверяются последовательно:

1. город пользователя × направление;
2. город пользователя × рынок гостиниц;
3. регион пользователя × направление;
4. регион пользователя × рынок гостиниц.

Если ни на одном уровне не найдено минимум пяти наблюдений, расстояние остаётся
`NULL`. Оценки на уровне страны не используются из-за высокой ошибки на
отложенной выборке.

Исходное значение сохраняется в `distance_raw`, результат — в
`distance_filled`. Поля `distance_is_imputed` и
`distance_imputation_level` показывают факт и уровень восстановления.

Подробное описание приведено в
[отчёте о заполнении расстояний](distance_imputation_report.md).

## Удержание

Когорта определяется месяцем первого наблюдаемого бронирования пользователя.
Показатель `booking_retention_rate` показывает долю пользователей когорты,
совершивших бронирование в конкретном месяце после первого бронирования.

Нулевой месяц равен 100% по определению. Показатель не является накопительным:
пользователь может учитываться в одном месяце и не учитываться в следующем.

Последние когорты имеют более короткое окно наблюдения. Поэтому их нельзя
напрямую сравнивать со зрелыми когортами на больших значениях
`months_since_first_booking`.

## Ограничения интерпретации

- Данные наблюдательные: различия между сегментами не доказывают причинность.
- Идентификаторы каналов, гостиничных рынков и направлений обезличены.
- В данных нет цены, расходов на привлечение, маржи, отмен, возвратов, способа
  оплаты и фактического проживания.
- Анализ удержания ограничен периодом наблюдения: для поздних когорт будущие
  повторные бронирования ещё неизвестны.
- `active_users` и `users` нельзя суммировать между группами без повторной
  дедупликации: один пользователь может присутствовать в нескольких каналах,
  месяцах, устройствах и сегментах.
- Связи, найденные в данных, должны проверяться A/B-тестами и дополнительной
  событийной аналитикой.

## Бронирования и value proxy

- `bookings` — число строк с `is_booking = 1`;
- `bookers` — число уникальных пользователей с бронированием;
- `booking_sessions` — число восстановленных сессий хотя бы с одним booking;
- `booking_value_proxy = 1` для hotel-only booking и `2` для package booking.

`booking_value_proxy` нужен только как относительный score. Его нельзя
интерпретировать как GMV, revenue, profit или валютную сумму.

## Восстановление distance

У `orig_destination_distance` около 35,9% пропусков. Заполнение выполняется
только по комбинациям географических ключей с достаточной поддержкой
(`min_support = 5`) и валидируется на holdout. Исходное значение сохраняется
отдельно, а в CORE есть признаки `distance_is_missing` и
`distance_is_imputed`.

Подробности: [distance_imputation_report.md](distance_imputation_report.md).

## Ограничения интерпретации

- данные наблюдательные: различия сегментов не доказывают причинность;
- идентификаторы каналов, рынков и destinations обезличены;
- в данных нет цены, маржи, отмен, возвратов и фактического проживания;
- retention ограничен 2013–2014 годами и страдает от right censoring;
- `active_users` в разных срезах нельзя бездумно суммировать: один пользователь
  может присутствовать в нескольких каналах, месяцах и сегментах;
- продуктовые гипотезы требуют A/B-проверки и дополнительной событийной
  разметки.
