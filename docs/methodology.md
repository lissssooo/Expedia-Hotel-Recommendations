# Методология

## Единица наблюдения

Исходная строка Expedia — агрегированная log row, а не гарантированно одно
физическое действие. Поле `cnt` хранит multiplicity, поэтому в проекте всегда
разделяются две системы объёма:

- `row_events = COUNT(*)`;
- `weighted_events = SUM(cnt)`.

Для каждой конверсии явно указано, какой знаменатель используется. Смешивать
row-based и `cnt`-weighted показатели нельзя.

## Слои данных

| Слой | Назначение |
|---|---|
| RAW | неизменённое представление исходных Parquet-файлов |
| STAGING | типизация, разбор дат, технические флаги качества |
| CORE | дедупликация, справочники, факты событий и бронирований, признаки |
| MARTS | агрегаты для продуктового анализа и BI |

Точный duplicate удаляется контролируемо: сохраняется первая строка по
стабильному `source_row_id`. В исходном полном train найдено 969 дубликатов.

## Даты

Рабочий диапазон продуктовых дат — с `2013-01-01` по `2016-12-31`
включительно. Строки с проблемными датами остаются в STAGING/CORE, но не
участвуют в метриках, для которых дата невалидна.

Большинство `year_month` в CSV хранится как дата первого дня месяца, например
`2014-07-01`. В двух финальных DataLens-выгрузках физический формат отличается:
`mart_package_profile` использует `YYYY/MM/01`, а
`mart_travel_calendar_daily` — `YYYY-MM`. При подключении к BI эти поля нужно
явно привести к типу Date/месяц, а не сортировать как произвольный текст.

Поведенческие event-метрики относятся к 2013–2014 годам. Финальный
`mart_travel_calendar_daily.csv` содержит непрерывную календарную ось
2012-02-15–2031-01-13, поскольку объединяет event, check-in и check-out роли;
после 2016 года в train нет фактической активности, поэтому на дашборде
следует применять рабочий фильтр периода.

## Сессии

В источнике нет надёжного `session_id`. Он восстановлен правилом
`gap_30m_v1`:

1. события сортируются внутри пользователя по `event_ts, event_id`;
2. новая сессия начинается при разрыве строго больше 30 минут;
3. одинаковые timestamps остаются в одной сессии;
4. `cnt`, destination, channel и параметры поиска не разрывают сессию.

Получено 12 242 331 сессия из 37 669 324 допустимых event rows. Это
аналитическая реконструкция, а не исходная сущность Expedia.

## Бронирования и value proxy

- `bookings` — число строк с `is_booking = 1`;
- `bookers` — число уникальных пользователей с бронированием;
- `booking_sessions` — число восстановленных сессий хотя бы с одним booking;
- `booking_value_proxy = 1` для hotel-only booking и `2` для package booking.

`booking_value_proxy` нужен только как относительный score. Его нельзя
интерпретировать как GMV, revenue, profit или валютную сумму.

## Восстановление distance

У `orig_destination_distance` около 35,9% пропусков. Заполнение выполняется
только по комбинациям географических ключей с достаточной поддержкой
(`min_support = 5`) и валидируется на holdout. Исходное значение сохраняется
отдельно, а в CORE есть признаки `distance_is_missing` и
`distance_is_imputed`.

Подробности: [distance_imputation_report.md](distance_imputation_report.md).

## Ограничения интерпретации

- данные наблюдательные: различия сегментов не доказывают причинность;
- идентификаторы каналов, рынков и destinations обезличены;
- в данных нет цены, маржи, отмен, возвратов и фактического проживания;
- retention ограничен 2013–2014 годами и страдает от right censoring;
- `active_users` в разных срезах нельзя бездумно суммировать: один пользователь
  может присутствовать в нескольких каналах, месяцах и сегментах;
- продуктовые гипотезы требуют A/B-проверки и дополнительной событийной
  разметки.
